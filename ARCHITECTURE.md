# Переезд Market Sandbox на Firebase

Документ описывает, что уже сделано в коде и что остаётся сделать на
стороне Firebase. Главный принцип: **Firebase отвечает за инфраструктуру,
а не за торговый движок**.

> Статус на момент этого репозитория: логика, описанная ниже, реализована
> в коде (`packages/engine`, `server`, `app`). Одно отличие от плана в этом
> документе: вместо отдельных Cloud Functions (`joinRoom`/`submitCommand`/
> `closeSession`/`getRoster`) вся эта логика теперь живёт прямо в сервисе
> на Cloud Run (`server/index.js`) как обычные HTTP-эндпоинты
> (`/api/joinRoom`, `/api/submitCommand`, `/api/closeSession`,
> `/api/roster/:roomId`), защищённые проверкой Firebase ID-токена. Причина
> объединения — упростить деплой до одного сервиса вместо двух, когда
> деплой делается вручную через веб-консоль, без командной строки. См.
> корневой `README.md` для пошагового гайда.

## 1. Что уже готово в приложении

Три шва, по которым проходит будущая граница клиента и сервера.

### Команды вместо результатов

Раньше интерфейс дёргал движок напрямую (`engine.submit`,
`engine.placeLimitOrder`, `engine.setProtection`). Теперь единственный
путь — `transport.send(command)`:

```js
{ type: 'TRADE',  action: 'BUY' | 'SELL' | 'CLOSE', notional?, fraction? }
{ type: 'LIMIT',  side, notional, limitPrice }
{ type: 'CANCEL_LIMIT', orderId }
{ type: 'PROTECT', stopLoss?, takeProfit?, clear? }
```

Клиент отправляет намерение, а не результат. Никаких «у меня теперь
позиция такая-то» и «начисли мне $120».

### Валидация внутри движка

`validateCommand(state, playerId, command)` проверяет ровно то, что
обязан проверять сервер. Проверено тестами — все эти команды
отклоняются:

| команда | ответ |
|---|---|
| покупка на $1 000 000 при балансе $1000 | недостаточно средств |
| отрицательный объём | неверный объём |
| закрытие без позиции | нет открытой позиции |
| стоп без позиции | нет открытой позиции |
| снятие чужой заявки | чужая заявка |
| неизвестный `type` | неизвестная команда |
| более 10 лимиток на игрока | слишком много заявок |

Плеча в модели нет: заявка не может превышать свободный кэш. Это не
только правило игры, но и защита замкнутости капитала — долг сломал бы
инвариант «сумма эквити всех участников и пула постоянна».

### Снапшот вместо доступа к состоянию

`createSnapshot(state, viewerId, { devMode, level })` — контракт между
сервером и клиентом. Все производные величины считает движок:
`equity`, `unrealized`, `settlement` (сколько дадут за закрытие сейчас),
`rank`. Клиент их только рисует.

Приватность проверена тестами:

- чужие `stopLoss` / `takeProfit` в снапшот не попадают;
- при `devMode: false` вырезается весь блок `debug` — и общий, и
  внутренности каждого бота.

Последнее важно для геймплея, а не только для безопасности: зная память
ботов, игрок торгует не рынок, а движок.

### Room и Transport

`Room` — будущая комната матча: движок + валидация + снапшоты. Сегодня в
ней 1 человек и 99 NPC, завтра 100 человек. **Market Engine между этими
случаями не меняется**: NPC и живые игроки — просто два источника команд.

`LocalTransport` крутит комнату в процессе. `RemoteTransport` —
намеренно нереализованная заготовка: без реального проекта Firebase её
нельзя ни собрать, ни проверить, а неработающий код, притворяющийся
рабочим, хуже честной заглушки. При переезде меняется одна строка:

```js
// было
engineRef.current = new LocalTransport({ startingCapital: capital });
// станет
engineRef.current = new RemoteTransport({ roomId, playerId, functions, firestore });
```

## 2. Замер, который меняет план

Первая же попытка посчитать вес снапшота показала, что наивная схема
«состояние комнаты → Firestore → все слушатели» не взлетит.

| уровень | содержимое | вес |
|---|---|---|
| `tick` | цена, давления, агрегаты толпы, ваша позиция | **0.99 КБ** |
| `roster` | 100 участников (имя, эквити, сторона, объём) | 8.9 КБ |
| `full` | всё, включая историю цен | 99 КБ |

Полный снапшот 10 раз в секунду — это 470 КБ/с на игрока и **29.5 МБ/с
на комнату из ста**. Для Firestore это неподъёмно и технически, и по
деньгам: там платят за чтение документа, а тут выходит 1000 чтений в
секунду на одну комнату.

Разделение по уровням даёт **1.8 МБ/с на комнату** — в 16 раз меньше:

```
tick   10 раз в секунду  →  10 КБ/с на игрока
roster  1 раз в секунду  →   9 КБ/с на игрока
full     при входе       →  99 КБ разово
```

**Отсюда вывод по стеку.** Firestore не годится как канал тиков.
Разделить так:

- **тиковый поток** — Realtime Database или WebSocket на Cloud Run;
- **Firestore** — профиль, баланс, история сессий, список комнат,
  результаты матчей, то есть всё, что меняется редко и должно
  переживать перезапуск.

## 3. Схема Firestore

```
users/{uid}
  displayName, createdAt
  wallet            число, ПИШЕТ ТОЛЬКО СЕРВЕР
  deposited         сколько всего пополнено
  stats { sessions, wins, totalPnL, best, worst }

users/{uid}/sessions/{sessionId}
  roomId, capital, equity, pnl, rank, trades, ticks
  startedAt, finishedAt

rooms/{roomId}
  status: 'waiting' | 'running' | 'finished'
  startingCapital, totalPlayers, seed
  createdAt, startedAt
  humanCount, npcCount

rooms/{roomId}/participants/{uid}
  joinedAt, capital, finalEquity

rooms/{roomId}/state/current        ← только если тики идут через Firestore
  снапшот уровня roster, 1 раз в секунду
```

Тиковое состояние в Firestore не хранится: см. раздел 2.

## 4. Cloud Functions

Все — callable, все под Firebase Auth и App Check.

```
joinRoom({ capital })        → { roomId }
    проверяет wallet >= capital, списывает взнос,
    создаёт участника, при необходимости поднимает комнату

submitCommand({ roomId, command })  → { ok, reason? }
    ровно то, что делает Room.send: валидация → движок →
    атомарная запись состояния комнаты

closeSession({ roomId })     → { equity, pnl, rank }
    закрывает позиции игрока по текущей цене,
    начисляет итоговый капитал на wallet,
    пишет запись в users/{uid}/sessions

getRoster({ roomId })        → снапшот уровня roster
```

Тик комнаты крутит **отдельный процесс на Cloud Run**, а не клиент.
Иначе скорость симуляции становится клиентским параметром: игрок,
управляющий частотой тиков, управляет рынком.

Не строить систему на триггерах вида «сделка → запись в Firestore →
триггер → пересчёт рынка → запись». Для торгового движка это лишняя
задержка и лишняя сложность.

## 5. Правила доступа

Ключевая мысль: **клиент не пишет ничего, что связано с деньгами**.

```
match /users/{uid} {
  allow read: if request.auth.uid == uid;
  allow write: if false;              // только Cloud Functions
}
match /users/{uid}/sessions/{id} {
  allow read: if request.auth.uid == uid;
  allow write: if false;
}
match /rooms/{roomId} {
  allow read: if request.auth != null;
  allow write: if false;
}
match /rooms/{roomId}/state/{doc} {
  allow read: if exists(/databases/$(database)/documents/rooms/$(roomId)/participants/$(request.auth.uid));
  allow write: if false;
}
```

App Check включить для Firestore, Realtime Database и Cloud Functions.
На iOS — App Attest, на Android — Play Integrity. Это отсекает запросы
не от настоящего приложения, но **не заменяет серверную валидацию**:
App Check подтверждает происхождение запроса, а не его честность.

## 6. Что перенести из этого прототипа на сервер

Файлы движка переезжают как есть, без изменений логики:

```
PriceEngine · LiquidityEngine · OrderEngine · PnLEngine
NPC-слой (архетипы, память, обучение)
Room · validateCommand · createSnapshot
```

Остаётся в приложении: рендер, ввод, локальный кэш снапшота.

Порядок работ:

1. Вынести движок в общий пакет TypeScript (`packages/engine`),
   импортируемый и приложением, и функциями.
2. Поднять Cloud Run-процесс, который держит комнаты в памяти и
   тикает их; Firestore — для персистентности.
3. Реализовать `RemoteTransport` по контракту `start / send / stop`.
4. Перевести `profileStore` на Firestore c записью только через функции.
5. Включить App Check и правила из раздела 5.

## 7. Чего пока нет и о чём стоит помнить

- **Восстановление после сбоя.** Если процесс комнаты падает, состояние
  в памяти теряется. Нужны периодические чекпоинты комнаты в Firestore
  и правило, что делать с открытыми позициями при падении.
- **Расхождение времени.** Сейчас тик равен 100 мс локально. На сервере
  тики должны идти по серверным часам, а клиент — интерполировать
  между снапшотами, иначе график будет дёргаться на плохой сети.
- **Отложенные команды.** При сетевой задержке команда исполнится по
  цене, отличной от той, что видел игрок. Это нормально для биржи, но
  интерфейс должен честно показывать цену исполнения — она уже есть в
  `execPrice` каждой сделки.
- **Пул как контрагент.** Сделки исполняются против пула, а не против
  встречных заявок участников. При живых игроках это стоит заменить на
  сведение встречных заявок; эквити пула в отладке показывает, сколько
  на этом накапливается.
